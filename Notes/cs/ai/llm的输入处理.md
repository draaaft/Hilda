传入的llm文字既不是直接变成“向量”，也不是先转成 Unicode 编码再变成向量。实际的中间步骤是 **Token（词元）及其整数 ID**。

### 真实流程：文字 → Token ID → 向量

当你向 LLM 发送一段文字时，底层大致经历以下步骤：

1.  **文字先被切分成 Token**：计算机确实无法直接存储“文字”本身。你输入的文字在系统底层首先是一串 Unicode 字符（及对应的 UTF-8 字节）。但模型不会直接去读这些字节。它会用一个叫 **Tokenizer（分词器）** 的组件，把文字切分成一个个 **Token**。Token 不一定是完整的字或词，可能是半个单词、一个汉字或一个标点。
2.  **Token 被映射为整数 ID**：每个 Token 在模型的“词表”里都有一个对应的唯一编号（整数 ID）。例如，某个 Token 可能对应 ID `12345`。这是模型处理文本时真正“看到”的数字形式，但它还不是向量，只是一个离散的索引编号。
3.  **Token ID 才被转化为向量（Embedding）**：模型用这个整数 ID 去一张巨大的“嵌入表（Embedding Matrix）”里查找，取出该 ID 对应的一行数字。这一行数字就是一个高维向量（比如 4096 个浮点数）。这个向量才是模型神经网络真正开始计算的输入。

### 为什么不是先转 Unicode 再转向量？

Unicode（或 UTF-8）是计算机**存储和传输**文字的通用标准，但在送入 LLM 之前，它通常会被 Tokenizer 处理掉。Tokenizer 的设计目标是把文本压缩成更紧凑、更有语义意义的片段。如果直接用 Unicode 码点或字节去查向量，序列会变得非常长，且单个字节或字符往往缺乏独立语义，模型学习效率很低。Token 机制相当于在“原始字符”和“最终向量”之间加了一层更高效的中间表示。

所以，你可以把流程简化为：**你看到的文字 →（Tokenizer）→ Token ID（整数）→（Embedding 查表）→ 向量（模型输入）**。

Tokenizer 把文字分割成 Token，并不是靠一条简单的规则，而是依靠一套在训练阶段就确定下来的“词表”和特定的切分算法。现代 LLM 几乎都采用**子词（Subword）** 级别的切分策略，核心思路是：**常见的词或词根保留为一个整体，罕见的词则被拆分成更小的、有意义的片段**。

具体实现主要依赖以下几种主流算法：

### 主流token切分算法

**1. 字节对编码（BPE）**
这是 GPT 系列等模型常用的方法。它的实现逻辑是在训练阶段“学”出来的：
*   **初始化**：先将所有文本拆成单个字符（或字节）。
*   **统计与合并**：统计语料中相邻字符对出现的频率，把**最高频的一对**合并成一个新的 Token。例如，如果“e”和“r”经常挨着出现，就合并成“er”。
*   **循环**：重复上述合并步骤，直到词表达到预设的大小。最终，高频词（如“the”）会成为一个 Token，而低频词（如“tokenizer”）则可能被拆成“token”和“izer”等片段。

**2. WordPiece**
这是 BERT 等模型采用的方法。它与 BPE 类似，但合并的标准不是频率，而是看合并后能否提升语言模型的概率。在切分时，它采用**贪心最长匹配**策略：给定一个词，它会从词表里寻找能匹配上的最长子词片段。如果一个词不在词表里，它会被拆成多个片段，后续的片段通常会加上 `##` 前缀来表示它是词的延续部分。

**3. Unigram / SentencePiece**
这类方法（常用于 LLaMA 等模型）的思路是“从大到小”地减枝。它先准备一个足够大的候选词表，然后通过统计方法，不断删除那些对整体语言模型贡献最小的 Token，直到词表缩减到目标大小。在推理时，它会根据概率模型，选择一种概率最高的切分方式。SentencePiece 的一个特点是，它把空格也当作普通字符处理（通常替换为 `▁`），这使得它不依赖特定语言的预分词规则，对中文、日文等没有空格分隔的语言特别友好。

### 为什么不用简单的“按空格切分”？

如果只用空格和标点切分（词级切分），会遇到两个致命问题：
*   **未登录词**：遇到词表里没有的新词、拼写错误或罕见词时，模型只能把它标记为“未知”（UNK），丢失信息。
*   **词表爆炸**：语言中词汇量巨大且不断增长，如果每个词都作为一个 Token，词表会大到无法管理。

子词切分通过把罕见词拆成常见的片段（如 `un` + `happy`），既控制了词表大小，又让模型能通过片段组合来理解新词的含义。

所以，Tokenizer 的切分过程本质上是**查表与匹配**：你输入的文字，会根据训练好的词表和算法（如 BPE 的合并规则或 WordPiece 的最长匹配），被切分成最符合该模型“语言习惯”的 Token 序列。

### tokenizer程序眼中的文字

从物理层面看，计算机里只有比特。但“tokenizer 程序眼中的文字”可以从两个层面来回答：**底层字节层面**和**tokenizer 处理时的抽象层面**。

### 底层：文字就是字节序列

当一段文字进入程序时，它首先是一串 **UTF-8 编码的字节**（或 UTF-16 等）。例如：

- 字符 `A` → 字节 `0x41`
- 汉字 `中` → UTF-8 字节 `0xE4 0xB8 0xAD`
- emoji `😀` → UTF-8 字节 `0xF0 0x9F 0x98 0x80`

程序读到的就是这些 `uint8` 数组。这一点没错，计算机不存储“文字”，只存储这些数字。

### Tokenizer 眼中的文字：取决于它的实现类型

关键点在于：**不同的 tokenizer 在“字节 → token”这一步走的路不同**。

**1. 基于字符/词表的 tokenizer（如传统 BPE on Unicode 字符）**

这类 tokenizer 会先把字节按 UTF-8 解码成 Unicode 码点序列，然后在**码点/字符层面**做切分和查表。它“眼中”的文字是一串 Unicode 码点（如 `U+4E2D`），每个码点再去词表里找对应的 token ID。此时字节已经被解码掉了。

**2. 基于字节的 tokenizer（Byte-level BPE，GPT 系列常用）**

这类 tokenizer **不做 UTF-8 解码**，直接把原始字节序列当作切分对象。它眼中的文字就是一串 `0~255` 的整数（字节值）。BPE 的合并规则作用在这些字节上。比如 `中` 的三个字节 `0xE4 0xB8 0xAD` 可能被合并规则组合成一个或多个 token。**这也是为什么 GPT 系列能处理任何字节序列、不会出现“未知字符”**——因为任何文字归根结底都是字节。

**3. SentencePiece（如 LLaMA）**

SentencePiece 通常先把文本规范化为 Unicode 字符序列（空格替换为 `▁`），然后在字符/子词层面操作。它内部也支持 byte fallback，遇到词表外的字符可以退回字节级处理。

### 所以，“tokenizer 眼中的文字”是什么？

可以这样概括：

- **物理上**：永远是字节数组。
- **逻辑上**：取决于 tokenizer 的设计。字符级 tokenizer 看到的是 Unicode 码点序列；字节级 tokenizer 看到的是 `0~255` 的字节整数序列；SentencePiece 看到的是规范化后的字符序列（带 `▁` 标记）。
- **输出上**：无论哪种，最终都变成一串**整数 token ID**，再拿去查 embedding 表变成向量。

换句话说，tokenizer 是“字节/字符”和“token ID”之间的翻译层。它并不“理解”文字，只是按照训练好的规则（合并表、词表、匹配算法）把输入的数字序列映射成另一串数字序列。**有的 tokenizer 会经过 Unicode 码点这一层，有的直接停在字节层，但最终都变成 token ID，再变成向量**。
